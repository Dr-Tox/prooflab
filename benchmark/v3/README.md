# ProofLab v3 release audit

V3 uses **optimized full-document analysis (Option B)**. Harper diagnostics are not publicly guaranteed to be independently segmentable; abbreviation/unit consistency and explicit temporal references have document dependencies. A sentence cache would require dependency tracking and a new equivalence contract. No incremental parser or partial-diagnostic reuse is introduced.

The transport keeps one active request and one latest queued request, settling replaced requests explicitly as superseded. Superseded replies never become clean results. One worker and one Harper instance remain alive. Native configuration is updated only when its complete configuration/dialect signature changes.

A single exact-input result can be reused for formatting-only requests. Text, the entire settings object and dictionary must match. Different content or configuration uses fresh full-document analysis. The cache is bounded to one entry, 128,000 text characters, 64,000 settings/dictionary-key characters, 1,000 findings and 256,000 result-content characters. Larger/uncertain results and mapping failures bypass it. Development diagnostics deliberately use fresh analysis. Nothing is persisted or transmitted. Real-engine tests compare cached and uncached results including rule IDs, categories, UTF-16 offsets, originals, replacements, atomic edits, review warnings and revisions across edits/profile/rule/dictionary changes.

## Scientific quality

Original curated scientific material nouns now include microbead/microbeads and related reagent/material vocabulary, with explicit regular plurals. No unfamiliar-looking token is automatically approved. The scientific spelling-error test remains active. This prevents the known harmful microbeads→microbe's/microbes alternatives without disabling spelling checks.

Bounded object relatives with an explicit inner subject/predicate and a clear matrix finite verb retain the outer subject head. Laboratory verb paradigms were extended with regular, documented English lemmas; arbitrary unknown verbs still abstain. No generic unknown-word-to-verb heuristic or speculative correction was retained. Deep/nested/ambiguous clauses and unknown verb paradigms remain limitations. Existing atomic corrections, scientific notation, negation, hedging, temporal review-only behavior, dictionaries and profiles remain intact.

Undo/redo share the existing bounded history and preserve text/HTML/caret snapshots. Native paragraph normalization remains part of reliable editor→worker UTF-16 input. No visual redesign or runtime dependency was added.

`quality.json` contains four original scientific paragraphs authored after rule development, including legitimate mixed tenses and scientific notation. It is a small engineering audit, not externally blinded or evidence of broad superiority. Detection and exact full corrections are reported independently; warnings never count as automatic corrections. Old benchmark references and first-evaluation reports remain unchanged. V3 results from those public, previously inspected sets are post-development regression audits.

## Performance reproduction

`performance.ts` runs one initialized real Harper instance, with three changed-text trials and three identical-text trials per approximate 1,000/5,000/10,000-word size. The public synthetic fixture is generated by `documents.ts`; this is a load probe, not another large linguistic corpus. For the previous implementation, archive source commit **5181e41** into `/tmp/prooflab-v3-baseline` and use the same installed dependency tree. Run `PERF_MODE=baseline node_modules/.bin/vite-node benchmark/v3/performance.ts`; run `PERF_MODE=v3` for v3. Native CPU is `process.cpuUsage`; memory is retained-process RSS/heap, not isolated browser/worker peak memory.

`browser-performance.mjs` compares static builds on loopback ports 4191/4192 using the existing Playwright Chromium. Each size has three changed-text and three format-only trials. It records actual worker round-trip latency, end-to-end latency including debounce, animation-frame gaps, long tasks, CDP task time, whole-browser process CPU and main-frame JS heap. CPU includes browser overhead, not just proofreading; main-frame heap excludes the WASM worker. Cold/warm startup repeats are separate. Browser/network caches, JIT and GC affect these small samples. Report ranges, not a speedup guarantee.

Fresh full-document work is not materially faster; scientific checks have priority over marginal timing. The large saving is **exact-repeat** analysis, such as formatting-only changes. Three-request transport stress settles the middle request and posts two analyses rather than three; normal debounced typing may coalesce less. The probe's paired exact-repeat workload has 50% cache eligibility and is not a prediction of manuscript-typing hit rate. Incremental/full fallback frequency is not applicable: all new text/settings/dictionaries use the full path.

Reports are local engineering artifacts with synthetic inputs. No runtime profiling or telemetry is enabled in the application. No comparison with Microsoft Word was performed.
